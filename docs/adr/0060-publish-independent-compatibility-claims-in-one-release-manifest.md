# Publish independent compatibility claims in one release manifest

Every Release 1 artifact is covered by a machine-readable Compatibility Manifest that keeps product, API, query, configuration, receiver, CRD, operator, storage, backup, and migration compatibility as separate evidence-backed claims. Product versions follow semantic versioning; patches cannot require persistent migration or break documented behavior. Public API and query `v1` contracts evolve additively with stable error and completion semantics, and older `v1` clients remain supported. A runtime Capability Statement lets new SDKs gate unsupported features before sending semantically invalid requests. Configuration reads the current and immediately previous minor schema and migrates only to a separate reviewed file. Persistent and backup Format Epochs declare exact read, write, and migration support through a published Migration Graph; older binaries refuse newer writable formats, and restore rejects unknown epochs before target mutation. Receiver conformance and operator N/N−1 compatibility remain independently pinned. Release CI exercises client skew, migrations, restore, upgrade, downgrade refusal, CRD conversion, operator skew, and receiver targets, and the signed manifest binds each claim to its evidence.
